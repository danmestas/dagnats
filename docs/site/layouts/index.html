Workflows that pick up exactly where they stopped.

dagnats is a workflow engine for work that has to finish: CI/CD pipelines, ETL jobs, notification automations, and agent loops when you need them. You describe the steps as a graph. Workers in any language do the work. The engine records every transition in NATS JetStream, so a crash, a deploy or a dead worker costs you nothing. It ships as one Go binary with no database to run.

What it does

You write the steps. dagnats makes sure every one of them finishes, in order, through crashes and restarts.

You describe the graph

A workflow is a set of steps and their dependencies, written as JSON or with the Go builder. Steps fan out, join, loop, sleep, wait for a person, or wait for an event.

Workers do the work

A worker is any process that handles a task type. Go workers use the SDK; anything else talks to the HTTP bridge. Run one worker or a hundred, on one machine or many.

The engine keeps the promises

Ordering, retries with backoff, step timeouts, concurrency limits, rate limits, sleeps and approvals. All of it is durable: state survives restarts because none of it lives in memory.

Ten minutes in

A workflow is a file. A worker is a function.

  func(ctx worker.TaskContext, name string) (string, error) {

  })

Step types

The hard parts of long-running work, as building blocks.

Each is a step type the engine understands, so you don't rebuild fan-out, waits, approvals and retries in every pipeline.

normalTask

Runs a handler once, with retries, backoff and a timeout.

 mapMap

Fans a task out over a list and joins the results.

 sleepSleep

For a duration, or until the next cron time in a named timezone.

 approvalApproval

Waits for a person to approve or reject, with an expiry.

 wait_for_eventWait for event

Parks the run until a matching event arrives, or a timeout.

 sub_workflowSub-workflow

Starts another workflow as a step and waits for it.

 respondRespond

Answers an HTTP request from inside the graph, so a workflow can be an API.

 plannerPlanner

Lets a handler add steps to the running graph.

 agent_loopAgent loop

Repeats a handler until it says done, checkpointed between iterations.
How it works

All state lives in JetStream. That is the whole architecture.

something happens

A trigger fires

Cron, a webhook, a NATS message, an HTTP request or another run finishing. It becomes an event on WORKFLOW_HISTORY.

the engine

The graph advances

The engine applies each event, saves a snapshot to the workflow_runs bucket, and queues the steps that are now ready.

your workers

Tasks run

Workers pull from TASK_QUEUES and publish the result back as an event. If a worker dies, its task is redelivered to another.

the clock

Time is a stream too

Sleeps, timeouts and retry delays are messages on SLEEP_TIMERS, not a scheduler you have to keep alive.

Clusters

One binary on a laptop. Three nodes across an ocean.

  • Clusters of three or five nodes. Every stream and bucket is replicated. Lose a node and runs keep completing on the others; it rejoins under its own name.
  • Health you can route on. /health/cluster reports members, quorum and per-stream sync, and returns 503 only when a replicated stream loses quorum.
  • Leases and leader election. Your services can hold a lease with a fencing token and forward requests to whoever owns a key, over plain NATS request/reply.

When to reach for something else

  • Sub-millisecond task routing: use a queue directly.
  • Independent batch jobs with no dependencies between them: a worker pool is simpler.
  • Multi-tenant hosting: dagnats is single-tenant by design.
  • SDKs: Go is native; other languages use the HTTP bridge for now.
  • dagnats is young (0.0.x). Expect breaking changes between releases.
